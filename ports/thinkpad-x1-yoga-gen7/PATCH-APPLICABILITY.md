# Graphics patch applicability: X1 Yoga Gen 7

Assessment against repository revision `99631db20ad841bb5d5f3934e4ffa4dc09f92dee`. “Candidate” means the source or a close hardware report makes reuse plausible; it does not mean validated on the Yoga.

| Component | Reference implementation and evidence | Yoga assessment | First port action |
|---|---|---|---|
| GPU presentation as Tiger Lake 9A49 | `kern_model.hpp` lists Alder Lake `46A8` as Iris Xe, but the Apple TGL driver path expects the GPU presented as `9A49`; XPS config does that at PCI 00:02.0. The Latitude 7430 issue reports the same spoof and Metal 2 on Tahoe 25G241. Device-table recognition is not proof of acceleration. | Candidate for the acceleration-only config. The Yoga PCI function is reported at 00:02.0, but its OpenCore device path and driver binding are not independently captured. | Keep absent from recovery. Verify PCI path and IORegistry on Yoga before enabling it in the experimental config. Do not copy XPS framebuffer properties wholesale. |
| NootedGreen non-TGL Gen12 path | `src/NootedGreen/kern_gen11.cpp` contains extensive `!isRealTGL` paths; the release config enables the Raptor Lake/Tahoe fix set and uses the host scheduler. The Latitude 46A8 report used that stack. | Strong reuse candidate: same GPU PCI ID and same CPU model have a community-reported Metal result. It remains a different Lenovo firmware/platform, and the Latitude had panel artifacts. | Begin from the exact release patch set. Change one Yoga-specific property at a time and retain verbose logging and a separate unaccelerated config. |
| Alder Lake DMC firmware | The current release uses `ngreen-dmc=adlp`; the source includes `FirmwareADLP.cpp`. The 46A8 Latitude report used this argument. | Candidate, not independently validated on the Yoga. | Retain only in the experimental profile after the first target boot confirms the expected firmware path and logs. |
| EU/subslice and L3 topology | The source defaults to 96 EU (12 traditional subslices × 8 EU) and 8 L3 banks. Boot arguments can override supported EU counts and L3 banks. Earlier fuse-reading attempts are documented as boot-hanging, so the default is not target autodetection. The Latitude report identifies its 46A8 as 96 EU. | The reported 96-EU nominal configuration is plausible, but the Yoga's active fuses, subslice mask, and L3 count are unknown. Same PCI ID does not prove identical active topology. | Read the Yoga's i915 SSEU/fuse report first. Record the observed values. Do not add topology overrides until evidence is available; compare explicit settings only in a reversible experimental config. |
| Gen12 kernel patches and scheduler | Most patches in `kern_gen11.cpp` are selected for the non-real-TGL path and target Apple's TGL 16.0.32 driver plus Tahoe 25G241 kernel ABI. Patch documentation says the byte patches fail on mismatched patterns. | Potentially reusable, but binary/build-specific and hardware behavior is experimental. A v2 recovery fix removed repeated hangs in the Latitude's reported tests; it did not remove that machine's scaled-mode/image artifacts. | Preserve the 25G241/16.0.32 gates. Do not set `XE_FORCE=1` or replace expected bytes to force a build. Capture kernel and user-space logs during staged tests. |
| eDP state, link training, framebuffer | `hwSetMode()` in `kern_gen11.cpp` writes `TRANS_DDI_FUNC_CTL_A=0x8A000106`, explicitly assuming a firmware-trained four-lane eDP link. `allocateDisplayResources()` also hard-codes four DBUF slices, ABOX mask `0b11`, and a four-channel LPDDR buddy-mask choice for the non-real-TGL path. The XPS experiments report unreliable eDP retraining after power cycle. | The Yoga's panel and shared display-engine family make reuse plausible, but its negotiated lanes/rate, VBT, memory topology and panel controls are unknown. These constants are unverified for the Yoga. | Capture VBT, `i915_display_info`, EDID and memory/display evidence first. Treat the four-lane write and DBUF/ABOX assumptions as blockers to enabling this path until compared with Yoga evidence. Do not transplant XPS panel timings. Test native mode before scaled modes. |
| Metal driver, libxedrv, shader compiler | `macos/mtl17-patches.json` holds offset-based patches; `patch-mtl17.py` verifies expected bytes at the listed offsets, not a full driver hash. The shader bridge uses Apple's TGL 16.0.32 compiler pieces with Tahoe's LLVM ABI. One patch at `0x065f12` is documented as an RPL-P reset-value adjustment. | These are mainly Tahoe/driver-bundle ABI adaptations, but the RPL-P allocation tweak is hardware-specific and its behavior on ADL-P 46A8 is unproven. Byte matching only validates the input bundle, not semantic suitability for this GPU. | Defer until kernel attachment and native eDP are proven. Build from legally obtained Apple binaries locally; do not commit them. Use exact 25G241 and 16.0.32 inputs, record hashes, and isolate/retest the `0x065f12` change on ADL-P. |
| Video acceleration plugin | The VA build checks a full SHA-256 for the 16.0.32 input and patches its device ID to 9A49. | Secondary to the goal of Metal desktop acceleration; no evidence it is needed for initial display bring-up. | Leave out of the first GPU milestone. |
| CPU identity, topology and power settings | The XPS uses a CPUID mask, CpuTopologyRebuild and an XPS-tuned `ngreenpm=22` profile for an i7-1360P with 4P+8E. | Not portable by assumption: the Yoga is an i7-1265U with 2P+8E and 12 logical processors. PL1, thermal, HWP and E-core behavior are unmeasured here. | Keep CPU topology and power experiments out of the initial graphics port. Investigate only if boot evidence shows they are needed. |

## Machine-specific components to replace

- ACPI: do not reuse `SSDT-XPS-I2C.aml`, its `_INI`/`_CRS` renames, or XPS GPIO paths. The Yoga reports SYNA8016 on I2C0 and WACF2200 on I2C1; derive ACPI paths and GPIO interrupts from its DSDT/SSDTs.
- USB: do not reuse `UTBDefault.kext` or the XPS `USBToolBox` map. Build from Yoga port enumeration.
- SMBIOS: do not copy the XPS MacBookPro16,2 identity or generate serials in this research scaffold.
- Audio and sensors: do not reuse the XPS SOF/SoundWire amplifier path or Dell sensor kexts for the Yoga's ALC287.
- Installation fallback: the repository's `config-install.plist` still has the XPS GPU spoof, ACPI tables and USB map. It is not a Yoga recovery config.

## Dependency and reproducibility findings

- NootedGreen is pinned by `install.sh` to commit `95f81898be65cb9f7b3d370ca78054be4cc8a62`; Lilu build headers are fetched as 1.7.2 while the EFI contains Lilu 1.7.3.
- MacKernelSDK is cloned at moving HEAD in the NootedGreen, HookCase and VoodooGPIO builders. VoodooGPIO source is pinned to `717ab2a`.
- OpenCore 1.0.8 is pinned for the `macserial` download in `make-efi.sh`; the tracked EFI binary's exact version still needs confirmation.
- No dependency pin should be invented for a Yoga build. Record the exact SDK, kext, OpenCore and Apple bundle versions used after a successful validation build.
